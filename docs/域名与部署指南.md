# 域名与部署指南（GitHub Pages 主站 · Netlify 镜像）

> 适用对象：「北京科技大学 寒假招生宣传小队 / 打道回阜队」里负责运维的同学（不写代码，也没有网站维护经验）。
> 站点形态：纯静态中文小队站（小队介绍 / 学生答疑 / 资料分享 等），无后端、无数据库。
> **主站**：<https://hanshuo007.github.io> —— 无水印，全站 200。
> **镜像**：<https://dadaohuifu.netlify.app> —— 可用，但右下角有 Powered by Netlify 角标。
> 仓库：<https://github.com/hanshuo007/hanshuo007.github.io>（公开，`main` 分支）。
> 构建：`node build.mjs`（零第三方依赖，不用 `npm install`），产物 `dist`；`site.config.mjs` 里的 `url` 已设为 `https://hanshuo007.github.io`。

## 为什么换成 GitHub Pages 当主站

- Netlify 免费计划**强制**显示 Powered by Netlify 角标，设置里是锁死的；
- 用 API 尝试关掉，直接返回 **422**（not available on this plan）；
- 角标跑在**隔离的 iframe** 里，站内 CSS 覆盖不了它。
- 换到 GitHub Pages 后页面上没有任何第三方水印，同一份 `dist` 还能继续发到 Netlify 做镜像。

## 一、选域名：判定清单

| 判定项 | 怎么判定 | 合格标准 |
| --- | --- | --- |
| 后缀 | 想清楚要 `.com`、`.cn`、`.net` 还是 `.me` | 小队站首选 `.com` |
| 是否必须 `.com` | 这网址会不会印在宣传单、贴进答疑群、做成二维码 | 要长期用、要给同学看，优先 `.com` |
| 长度 | 数主域名（不含后缀）的字符数 | 4–15 个字符；整体不超过 25 个（二维码更好扫） |
| 易读易念 | 电话里念一遍，让同学复述 | 能一次听对、不会拼错 |
| 拼写歧义 | 有没有 `-`、`0` 与 `o`、`1` 与 `l` | 尽量不用；必须用时只用一处 |
| 小队可识别 | 是否含 `ustb` 或队名拼音 | 一眼看出是北科大寒招小队 |
| 记忆成本 | 隔一天还能默写吗 | 能 |
| 价格与续费 | 分别看首年价与**续费价** | 只看续费价能否接受；**价格以注册商页面为准** |
| 续费陷阱 | 是否自动续费、是否绑多年优惠 | 打开自动续费防丢域名 |
| 商标与校名风险 | 是否像某品牌或像学校官网 | 不带他人商标，别做得像「北科大官网」 |

两条只对本站有意义：招生场景域名常进海报与二维码，**短**比好看更重要；别为「显专业」选生僻后缀，续费会暴涨。

| 准备项 | 说明 | 多久 |

| 一个 GitHub 账号 | 主站要用（用户名会进默认网址，**起好别再改**）；用户名里不要有连续短横线，否则 Linux 用户访问会报错（官方说明） | 几分钟 |

## 三、备案说明：什么时候需要，什么时候不需要

判断标准一句话：**看网站最终由哪台机器、在哪个地区对外提供服务。**

### 3.1 现状

主站托管在 GitHub Pages，内容从 GitHub 的境外节点分发，**不落在中国大陆境内服务器上**。这种情况通常不需要 ICP 备案。

### 3.2 什么情况会变成「需要备案」

- 搬到**中国大陆境内**云服务器（ECS / CVM / 轻量应用服务器）；
- 接入**境内** CDN 节点或境内对象存储静态托管；
- 用境内「建站」类产品；
- 交给**学校网络中心托管到校园网服务器**（同属境内托管，还要走学校审批）。

备案按**接入服务商**办理，境内服务商开通服务前会要求已备案域名；境外托管没有这个环节。

### 3.3 容易混淆的点

- **买域名 ≠ 要备案**：境内注册商要的是**实名认证**。
- 注册商在境内、托管在境外：仍是「境外托管」。
- 备案不是一劳永逸：换接入商/地域要变更。
- 拿不准就问接入商或学校网络中心。官方入口：<https://beian.miit.gov.cn/>（打开慢或被拦属常见现象）。

### 3.4 一条实操建议

如果未来有搬到境内（或交给学校托管）的可能，**买域名时就注册在境内注册商并完成实名认证**，日后备案时域名这一环不会卡住。境外注册商的域名，部分省份备案流程更麻烦，**以接入商要求为准**。

### 3.5 如果要在国内访问更快

先说结论：**`github.io` 在国内访问一般**；绑自己的域名会好一些，但**不保证**——任何境外托管都可能遇到延迟、限速甚至打不开。

三条路，按改动量排序：

| 路线 | 做什么 | 要不要备案 | 代价 |
| --- | --- | --- | --- |
| **A. 保持 GitHub Pages** | ①绑自己的域名（别只发 `*.github.io` 网址）②字体、统计脚本等第三方资源改成站点自带 | 不需要 | 零成本；高峰期仍可能慢或打不开 |
| **B. 前面加一层 CDN** | 在域名前挂一个 CDN（境外节点），缓存静态文件 | 不需要（用境外 CDN 节点时） | 多一层配置与排查；**缓存会让更新延迟**，需要会清缓存；CDN 自身也可能被干扰 |
| **C. 换境内对象存储 + CDN** | 把 `dist` 传到境内对象存储，挂境内 CDN，域名指过去 | **需要** | 国内最快最稳，但要备案（需时间）、多维护一套账号，每次发布传两处 |

建议：先做 A；只有「答疑群里同学经常打不开」成为真问题时，才值得为 B / C 付出复杂度或备案成本。

## 四、仓库名与站点类型：用户站 vs 项目站

**这是本站最容易踩、踩了全站断链的坑，单独成节。**

GitHub Pages 有两种站点，官方对照表如下：

| 项目 | 用户 / 组织站 | 项目站 |
| --- | --- | --- |
| 源码位置 | 仓库名**必须**是 `<owner>.github.io` | 仓库里任意文件夹 |
| 数量限制 | 每个账号最多 1 个 | 每个仓库最多 1 个 |
| 默认网址 | `https://<owner>.github.io`（根路径） | `https://<owner>.github.io/<仓库名>`（带前缀） |

### 4.1 为什么我们的仓库必须叫 `hanshuo007.github.io`

本站所有站内链接都是**以 `/` 开头的绝对路径**（例如 `/qa/`、`/assets/style.css`、`/rss.xml`）。这种写法的前提是：**站点发布在域名根路径上**。

只有「用户站」发布在根路径。所以：

- 仓库名是 `hanshuo007.github.io` → 站点在 `https://hanshuo007.github.io/`，此时 `/qa/` 指向 `https://hanshuo007.github.io/qa/`，**正好对**；
- 仓库名是别的（项目站）→ 站点在 `https://hanshuo007.github.io/<仓库名>/`，但页面里 `/qa/` 依然解析到 `https://hanshuo007.github.io/qa/`（少了仓库名那一段）→ 首页能开、**所有子页面、样式、RSS、sitemap 全部 404**。

这就是本仓库当初从 `dadaohuifu` **改名**为 `hanshuo007.github.io` 的原因。

### 4.2 一定要记住的三条

1. 用户站的仓库名必须**严格等于** `<你的GitHub用户名>.github.io`，大小写也要一致。
2. 一个 GitHub 账号**只能有一个**用户站（官方限制）。
3. 如果哪天你新建仓库重做一次，**别起名 `dadaohuifu` 之类的项目名**——那会自动变成项目站，回到「全站断链」的老路。

### 4.3 万一只能用项目站怎么办

那就必须把站内的绝对链接改成相对路径，或者在构建时注入 base path（本项目 `build.mjs` 没有做这件事）。**改造成本远大于改仓库名**，所以本站的选择就是：仓库名必须是用户站仓库名。

### 4.4 怎么验证没踩坑

浏览器打开 <https://hanshuo007.github.io>，看地址栏：**不应出现 `/仓库名/` 这样的前缀**；然后随便点两个页面，能打开且样式正常，就说明根路径是对的。

## 五、部署：GitHub Actions 自动发布

### 5.1 一次性设置：把 Source 设成 GitHub Actions

1. 打开仓库 → **Settings** → 左侧 **Pages**。
2. 在 **Build and deployment** 下，**Source** 选 **GitHub Actions**（官方原文就是这样一项）。
3. 设好之后不需要你再点发布——推送到 `main` 就会自动构建并发布。

> 如果这里是 **Deploy from a branch**（从分支发布），那走的是另一套机制（需要把构建产物提交进仓库，或用 `docs/` 目录），**和本项目的工作流不匹配**。以设置页显示为准，认准 **GitHub Actions** 这一项。

### 5.2 仓库里的工作流做了什么

文件：`.github/workflows/deploy.yml`，在推送到 `main` 或手动触发时运行，包含两个 job：

| job | 干什么 |
| --- | --- |
| **pages**（主站） | checkout → 装 Node 20 → `node build.mjs` 构建 → `node scripts/check-links.mjs` 自检 → `actions/configure-pages` → `actions/upload-pages-artifact`（上传 `dist`）→ `actions/deploy-pages` 发布 |
| **netlify**（镜像） | checkout → 装 Node 20 → 再构建一次 → `npx netlify-cli deploy --prod --dir=dist` 把同一份产物发到镜像站 |

pages job 的权限必须包含 **`pages: write`** 与 **`id-token: write`**，并挂 **`github-pages`** 环境——这是官方对 `deploy-pages` 的硬性要求（缺了就会报权限错误，见第八节）。

### 5.3 在哪看运行记录

仓库顶部 → **Actions** 标签 → 左侧选 **Deploy** → 点最近一次运行：

- 两个 job 都变绿勾 = 成功；
- 点 **pages** → 展开 **Deploy artifact** 那一步，能看到部署地址与耗时；
- 某一步红叉 = 失败，点开那一步看日志（最常见的两类：构建报错、权限不足）。

### 5.4 第一次发布要等多久

- 构建 + 自检：通常几十秒；
- `deploy-pages` 发布完成后，Pages 一般一两分钟内对外可见；
- 如果你同时改了自定义域名的 DNS，**DNS 变更最多 24 小时传播**（官方说明），那段时间里不同网络看到的结果可能不一样。

### 5.5 免费额度（官方数字）

| 项目 | 限制 |
| --- | --- |
| 源仓库 | 建议不超过 **1 GB** |
| 已发布站点 | 不得大于 **1 GB** |
| 单次部署 | 超时上限 **10 分钟** |
| 流量 | **软限制 100 GB / 月** |
| 构建频率 | **软限制 10 次 / 小时**，但**用自定义 GitHub Actions 工作流构建时不适用这一条**（本项目正是 Actions 构建） |

还有一条运维要知道的：请求过于频繁时 GitHub 可能返回 **429** 限流。

## 六、绑定自定义域名（本节是重点）

### 6.1 先在仓库设置里填域名

1. 仓库 → **Settings** → **Pages**。
2. **Custom domain** 里填你的域名（例如 `example.com`）→ **Save**。
3. 官方明确说明：**如果是从分支发布**，保存会往源码分支根目录提交一个 `CNAME` 文件；**如果你用的是自定义 GitHub Actions 工作流，则不会创建 `CNAME` 文件，已有的 `CNAME` 文件也会被忽略、且不需要**。

   本站用的是 Actions 工作流 → **所以你不需要维护 `CNAME` 文件**，域名信息保存在仓库的 Pages 设置里，不要到仓库里找它、也不要自己加。

> 顺序很重要：官方建议**先把域名加到 GitHub，再去改 DNS**。反过来做，别人有可能抢注你的子域名。

### 6.2 DNS 记录表（值来自官方文档，可直接照抄）

**根域名 `example.com`（apex）**：官方要求至少配一条 `ALIAS` / `ANAME` / `A` 记录。绝大多数国内 DNS 只支持 A 记录，就照下面四条配：

| 类型 | 名称（主机记录） | 值 | TTL |
| --- | --- | --- | --- |
| `A` | **@**（根域名） | `185.199.108.153` | 自动 / 600 |
| `A` | **@** | `185.199.109.153` | 自动 / 600 |
| `A` | **@** | `185.199.110.153` | 自动 / 600 |
| `A` | **@** | `185.199.111.153` | 自动 / 600 |

可选 IPv6（官方建议用 AAAA 时同时保留 A 记录，因为 IPv6 普及慢）：

| 类型 | 名称 | 值 |
| --- | --- | --- |
| `AAAA` | **@** | `2606:50c0:8000::153` |
| `AAAA` | **@** | `2606:50c0:8001::153` |
| `AAAA` | **@** | `2606:50c0:8002::153` |
| `AAAA` | **@** | `2606:50c0:8003::153` |

**www 子域名**：

| 类型 | 名称（主机记录） | 值 | TTL |
| --- | --- | --- | --- |
| `CNAME` | `www` | `hanshuo007.github.io` | 自动 / 600 |

官方提醒两点：CNAME 要指向 **`<用户名>.github.io`**（**不要带仓库名**，也不要指向 `*.pages.github.io` 那个内部域名）；根域名和 www 都配好之后，GitHub Pages 会**自动在两个地址之间跳转**（你在 Custom domain 里填哪个，另一个就跳到它）。

写法提醒：

- 值不要带 `https://`、不要带结尾斜杠。
- 根域名位置不要同时放 A 和 CNAME；多出来的旧记录会让校验失败。
- 各家 DNS 的「名称」写法不同（主机记录填 @ 与 www 最常见）。**若界面与上文不同，就找含「记录类型 / 主机记录 / 记录值」的入口，按设置页提示的格式填。**
- 官方还明确不建议用通配符记录（`*.example.com`），有被他人接管子域名的风险。

### 6.3 打开 Enforce HTTPS（强制跳转）

域名校验通过后，Pages 设置里会出现 **Enforce HTTPS** 勾选框，勾上即可——它会把 http 请求透明地重定向到 https。

三个时间预期（都是官方原文）：

- **最多可能需要 24 小时**，这个勾选框才会变为可选；
- 配置好自定义域名后，**最多 1 小时**站点才能通过 HTTPS 访问；
- 如果之后又改了 DNS，**可能需要把自定义域名移除再重新添加**一次，才会重新触发证书签发。

若你用了 CAA 记录，官方要求至少有一条 CAA 允许 `letsencrypt.org`，否则站点无法通过 HTTPS 访问。

### 6.4 换域名后必须做的事：改 `site.config.mjs` 并重新构建

RSS 和 sitemap 里的链接是在**构建时**写死的，来源是 `site.config.mjs` 里的 `url`。所以换域名时：

1. 打开 `site.config.mjs`，把 `url` 改成新域名（本站现在是 `https://hanshuo007.github.io`）；
2. 本地跑 `node build.mjs`；
3. 打开 `dist/rss.xml` 和 `dist/sitemap.xml`，确认里面的域名是新的；
4. 提交并推送，让 Actions 重新发布。

**只改 DNS 不改这里**，结果是：页面能访问，但 RSS 阅读器、搜索引擎拿到的还是旧域名——这种问题很久都不会有人发现。

### 6.5 怎么确认 DNS 真的生效

Windows 自带没有 `dig`（官方明确提示），用 PowerShell 的 `Resolve-DnsName`：

```powershell
Resolve-DnsName example.com -Server 1.1.1.1
Resolve-DnsName www.example.com -Server 1.1.1.1
```

**看到什么算成功**：`example.com` 返回上面四个 `185.199.x.153` 之一；`www` 那条能看到指向 `hanshuo007.github.io` 的别名；仓库 Settings → Pages 里域名旁的提示不再是 DNS 校验失败。

### 6.6 以后在同一域名下加页面，会影响域名吗？

**不会。** 域名绑定在仓库的 Pages 设置里，与页面文件无关：

- 新增/删除页面、改文案、换配色，**都不用动域名与 DNS**；
- 只需要重新构建并推送（第五节的 Actions 会自动发布）；
- 新页面能不能打开，只取决于 `dist` 里有没有对应文件；
- 唯一别动的是：**仓库名**（见第四节）和 **Pages 设置里的域名**。

## 八、常见故障排查表

| 现象 | 最可能的原因 | 怎么确认 | 怎么修 |
| --- | --- | --- | --- |
| 首页能开，但**子页面全部 404**、样式也丢 | 站点被当成**项目站**发布了（网址里带 `/仓库名/` 前缀），而页面里全是 `/` 开头的绝对链接 | 看地址栏有没有仓库名前缀；F12 看 CSS 请求 404 的路径 | 仓库改名成 `<用户名>.github.io`（第四节）；这是唯一根治办法 |

| Pages 设置里 **DNS check unsuccessful** | A 记录没配齐四条、值抄错、根域名上还有旧的 CNAME、或 DNS 还没传播（最多 24 小时） | 用 `Resolve-DnsName example.com -Server 1.1.1.1` 对照四个官方 IP | 按 6.2 补齐/改对记录，删掉冲突记录，等传播后再看 |

| Actions 报**权限不足**（pages / id-token） | 工作流缺少 `pages: write` 或 `id-token: write`，或没挂 `github-pages` 环境 | 打开失败的那次运行，看报错的那一步与 job 的 `permissions` | 在 pages job 上补 `permissions: pages: write / id-token: write` 与 `environment: github-pages`（仓库里 `deploy.yml` 已正确配置，改坏时对照它） |
| 推送了但 Actions **没跑** | 推的不是 `main`；或改了工作流却没在默认分支上生效 | Actions 标签里看有没有新的运行记录 | 确认分支与推送结果；必要时在 Actions 里手动 **Run workflow** |
| 部署成功但**页面是旧的** | 浏览器缓存；或看的是镜像/旧标签页；或构建产物确实是旧的 | 看 Actions 最近一次运行的时间与提交号；无痕窗口打开 | Ctrl+F5 或无痕窗口；确认这次运行对应你最新提交；必要时重跑工作流 |
| 国内访问慢，或 `github.io` 被干扰 | 境外托管的网络现实 | 换手机流量/换网络对比；只发 `github.io` 网址时更明显 | 先绑自己的域名（6.1），再把第三方资源改成自托管；见 3.5 的三条路 |

## 九、日常发布、回滚与换届交接

### 9.1 改内容之后的固定动作

1. 改页面文件（例如「小队介绍」补一句寒招行程）。
2. 本地构建并自检：
   ```bash
   node build.mjs
   ```
   打开 `dist/index.html` 把每个页面点一遍（能提前发现链接与路径问题）。
3. 提交并推送：
   ```bash
   git add .
   git commit -m "update: 小队介绍补入寒招行程"
   git push
   ```
4. 仓库 → **Actions** → **Deploy**：看到新运行自己开始跑，两个 job 变绿勾。
5. **看到什么算成功**：<https://hanshuo007.github.io> 打开就是新内容；镜像站稍后也会更新（同一个工作流里的 netlify job）。
6. 看不到新内容：先 Ctrl+F5 / 无痕窗口；仍不对看第八节「部署成功但页面是旧的」。

### 9.2 回退到旧版本（Pages 没有回滚按钮）

两种做法，按场景选：

- **只是想重新发布旧的构建**：仓库 → Actions → 找到上一次成功的那次 **Deploy** 运行 → 右上角 **Re-run all jobs**。官方说明：可以在**初次运行后 30 天内**重跑整个运行、失败 job 或指定 job。
- **代码也要退回去**（推荐，更彻底）：`git revert` 那个提交 → `git push` → 等新的 Actions 运行变绿。这样仓库状态和线上一致，下一个人看到的历史也是对的。

> 注意：直接重跑旧运行只是把旧产物又发了一遍，**仓库代码还是新的**。过几天有人再推一次代码，线上又变回新版——所以要真正回退，用 `git revert`。

### 9.3 换届交接（小队站特别重要）

- 交接清单至少包含：GitHub 用户名与账号（**账号丢了站点就等于丢了**）、仓库地址、Actions 里的 secrets（`NETLIFY_AUTH_TOKEN` / `NETLIFY_SITE_ID`）、自定义域名与 DNS 账号、域名续费日期、`site.config.mjs` 里的 `url`。
- 域名开自动续费，日历里记到期前 2 周提醒——域名过期被释放是最贵的一类事故。
- 换人时把旧 token/secret 轮换掉：Netlify 的 token 在账号设置里吊销后重新生成，再更新到仓库 secrets。
- `dist/` 是构建产物，应被 `.gitignore` 忽略（本站已如此），仓库里只留源码。
