# 域名与部署指南

> 适用对象：「北京科技大学 寒假招生宣传小队」里负责运维的同学（不写代码，也没有网站维护经验）。
> 站点形态：小队的官方小队站，纯静态中文站点，目前包含「小队介绍」「学生答疑」「资料分享」三个页面；站内是纯静态 HTML，无后端、无数据库。
> 构建方式：在仓库根目录执行 `npm run build`（内部调用 `node build.mjs`），不需要 `npm install`，产物输出到仓库根的 `dist/` 目录。
> 托管平台：Cloudflare Pages。
>
> 阅读方式：第一次配置请从「一」按顺序读到「八」，配置完成后日常只看「九」。
> 全文中的 `example.com` 请替换成你自己的域名，`ustb-winter-team` 请替换成你在 Cloudflare Pages 上的项目名（本文统一用它举例，你可以换成小队名拼音）。

## 一、选域名：判定清单

一条一条过，全部打勾再买。域名买错要换，等于前面的配置全部重做。

| 判定项 | 怎么判定 | 合格标准 |
| --- | --- | --- |
| 后缀 | 先想清楚要 `.com`、`.net`、`.me`、`.dev` 还是 `.cn` | 小队站首选 `.com`；`.com` 被占了再考虑 `.cn` / `.net` / `.me` |
| 是否必须 `.com` | 问自己：这个网址会不会印在宣传单、贴进答疑群、做成二维码 | 要给同学看、要长期用，优先 `.com`，它最容易被记住和信任 |
| 长度 | 数一数主域名（不含 `.com`）有几个字符 | 建议 4–15 个字符；整体不超过 25 个字符（二维码更容易扫、念出来更短） |
| 易读易念 | 在电话里念一遍，让同学复述一次 | 对方能一次听对，且不会拼错 |
| 拼写歧义 | 检查有没有连字符 `-`、数字 `0` 与字母 `o`、`1` 与 `l` | 尽量不用连字符和数字；必须用时只用一处 |
| 小队可识别 | 域名里是否含 `ustb` 或小队名拼音 | 一眼能看出是北科大寒招小队；不要用和学校无关的随手词 |
| 记忆成本 | 隔一天不看，还能默写出来吗 | 能默写 |
| 价格与续费 | 注册商页面上分别看「首年价」和「续费价」 | 只看续费价是否能接受；促销首年价没有意义，价格**以注册商页面为准** |
| 续费陷阱 | 检查是否自动续费、是否有「多年优惠」绑定、转入转出是否有费用 | 打开自动续费防丢域名；不接受需要一次性买 5 年才便宜的方案 |
| 商标与校名风险 | 搜一下这个词是否是知名品牌名；队名缩写是否会被误认为学校官方主站 | 不带他人商标；也不要用看起来像「北科大官网」的名字，避免误导 |
| 拼音 vs 英文 | 中文同学能看懂拼音，英文单词更好念 | 二选一即可，别混着写 |

两条只对本站有意义的判断：

- 招生宣传场景下，域名常被写进海报和二维码，**短**比「好看」更重要。
- 不要为「看起来专业」去选生僻后缀，新手最容易踩的坑是续费价格暴涨。

## 二、在哪买：四个渠道的取舍与注册前准备

### 2.1 四个渠道对比

| 渠道 | 适合谁 | 优点 | 要注意 |
| --- | --- | --- | --- |
| Cloudflare Registrar | 已经决定用 Cloudflare 托管的人 | 按成本价卖、无溢价、默认隐私保护、一键 DNSSEC；官方文档明确说明「所有通过 Cloudflare Registrar 获得的域名都使用 Cloudflare 的 nameserver」，也就是说**买了就等于把 DNS 托管在 Cloudflare 上了**，本指南第五部分里最省事的做法自动成立 | 不支持国际化域名（IDN，即含 `à` `ü` 这类字符的域名）；可选后缀比大注册商少；注册/转入前必须先有一个**已验证的账号邮箱**；付费需要能用于国际支付的卡 |
| 阿里云 | 想要中文界面、支付宝付款的人 | 全中文、支付宝/微信付款、客服说中文、`.cn` / `.com` 齐全 | 需要做域名**实名认证**（境内注册商的通行要求，认证通过后才算注册成功）；DNS 默认在阿里云云解析，想把根域名接到 Pages 需要额外折腾（见 5.3） |
| 腾讯云 | 同上，习惯腾讯系产品的人 | 全中文、微信支付、域名与 DNSPod 打通 | 同样需要实名认证；根域名接 Pages 的限制同阿里云 |
| Namecheap | 想要英文界面但不想被 Cloudflare 后缀限制的人 | 后缀选择多、常有大额首年优惠、whois 隐私免费 | 促销首年便宜、**续费会明显变贵**；英文界面；国际支付 |

给你的建议（三选一，按省事程度排序）：

1. **Cloudflare Registrar**：和托管平台同一家，DNS 天然就在 Cloudflare，第五部分只需要做「加域名」一步。缺点是界面全英文。
2. **阿里云 / 腾讯云**：全中文、付款方便、有客服，适合完全不想碰英文界面的人。代价是根域名接入 Pages 这一步要多做一次 nameserver 迁移。
3. **Namecheap**：只在你想要的域名后缀 Cloudflare 不卖时才选。

注意：域名是**小队共用的资产**，建议用小队公共邮箱（或能长期交接的邮箱）注册，并把账号密码交给下一届负责人。用个人 QQ 邮箱注册、人毕业了就找不回，是小队站最常见的「死域名」原因。

### 2.2 注册前要准备什么

| 准备项 | 说明 | 大概要多久 |
| --- | --- | --- |
| 一个能长期收信的邮箱 | 注册商和 ICANN 都会往这个邮箱发验证信。Cloudflare 明确要求账号邮箱**已验证**；未验证的注册人邮箱会导致域名被挂起（nameserver 被换成停放服务器），验证后才恢复 | 当场，几分钟 |
| 实名认证材料（境内注册商） | 阿里云 / 腾讯云注册 `.com` `.cn` 等域名需要提交实名信息并等待审核。具体材料清单**以注册商页面为准** | 通常当天内，个别情况需要 1–2 个工作日 |
| 支付方式 | Cloudflare / Namecheap：需要支持国际支付的信用卡或对应支持的支付渠道；阿里云 / 腾讯云：支付宝、微信、银行卡 | 当场 |
| 决定好的域名 | 提前想好 2–3 个备选，避免第一个被占后临时乱选 | — |
| 一个小队专用的 Cloudflare 账号 | 部署和 DNS 都在这里操作，用同一个邮箱注册 Cloudflare | 几分钟 |

价格一律不写具体数字：**以注册商页面为准**。看价格时看「续费价」那一列。

## 三、备案说明：什么时候需要，什么时候不需要

这一节只讲边界，不做法律结论。判断标准只有一句话：**看你的网站最终由哪台机器、在哪个地区对外提供服务。**

### 3.1 本项目的现状

小队站托管在 Cloudflare Pages，内容分发在 Cloudflare 的全球节点上，**不落在任何中国大陆境内的服务器上**。这种情况下，通常不需要办理 ICP 备案，域名可以正常解析和访问。

### 3.2 什么情况会变成「需要备案」

只要出现下面任一情况，就该把备案当成前置条件，先备案再切流量：

- 把站点搬到**中国大陆境内**的云服务器（ECS / CVM / 轻量应用服务器等）。
- 给站点接入**中国大陆境内**的 CDN 加速节点、或境内的对象存储静态托管。
- 用境内的「网站建设 / 建站」类产品托管内容。
- 把站点交给**学校网络中心托管到校园网服务器**——这同样属于境内托管，不但要备案，通常还要走学校的审批流程。

原因很直接：备案是**按接入服务商**办理的，境内服务商在给你开通网站服务前会要求你提供已备案的域名。境外托管没有这个接入环节，所以也就没有这个前置条件。

### 3.3 几个容易混淆的点

- **买域名不等于要备案**。域名注册（境内注册商）要做的是**实名认证**，那是域名管理的要求；备案是网站接入环节的要求，两件事不同。
- **域名注册商在境内、服务器在境外**：仍然是「境外托管」，通常不需要备案。
- **备案不是一劳永逸**：换了接入商、换了服务器地域，备案信息要相应变更。
- **不确定就问接入商**：如果你日后打算用境内服务，直接问对应云厂商的备案控制台/客服，或问学校网络中心，他们的口径才是最终口径。官方备案系统入口：<https://beian.miit.gov.cn/>（打开慢或被拦截属于常见现象，换网络再试）。

### 3.4 一条实操建议

如果未来有搬到境内（或交给学校托管）的可能，**在买域名时就把域名注册在境内注册商并完成实名认证**，这样日后备案时域名这一环不会卡住。域名在境外注册商的情况下，部分省份的备案流程会更麻烦，具体**以接入商要求为准**。

## 四、两条部署路径

先说清一件**不能反悔**的事（Cloudflare 官方文档两处都明确写了）：

- 选了 **Direct Upload（直接上传）**，之后**不能**改成 Git 集成，只能新建一个项目重来。
- 选了 **Git 集成**，之后**不能**改成 Direct Upload；但可以关闭自动部署，改用 Wrangler 手动部署。

所以：**如果小队打算把站点长期维护下去、并且已经有 Git 仓库，走路径 A；如果完全不想碰 Git，走路径 B。**

### 4.1 路径 A：连接 Git 仓库自动部署

前提：站点代码已经推送到 GitHub 或 GitLab 仓库，且仓库根目录有 `package.json` 与 `build.mjs`。

1. 登录 Cloudflare，进入 **Workers & Pages** 页面。
2. 点 **Create application** → **Pages** → **Connect to Git**。
3. 选 **GitHub**（或 **GitLab**），按提示授权。首次会要求你授权 Cloudflare 访问仓库。
4. 在列表里选中小队站的仓库 → **Install & Authorize** → **Begin setup**。
5. 在 **Set up builds and deployments** 页面填写：
   - **Project name**：例如 `ustb-winter-team`。这决定默认网址 `ustb-winter-team.pages.dev`，**起好后不要再改**（改项目名会换掉默认域名）。
   - **Production branch**：填主分支名，通常是 `main`。
   - **Build command**：填 `npm run build`。
   - **Build output directory**：填 `dist`。
   - **Root directory**：如果站点代码在仓库的子目录里（例如仓库根下有个 `website/`），填那个子目录名；代码就在仓库根目录则留空。
6. 点 **Save and Deploy**，等构建。
7. **看到什么算成功**：项目里 **Deployments** 列表最上面出现一条 Production 部署，状态是 **Success**；点开它给的 `*.pages.dev` 网址能看到「小队介绍」页面。

两个关于构建命令的注意点：

- 本项目**没有第三方依赖**，所以不需要在构建流程里额外配置 `npm install`。如果 Cloudflare 在构建日志里自动跑了 `npm install`，那也没关系，它会正常结束。
- 如果你的仓库里**没有** `package.json`（例如你打算把构建好的 `dist` 直接提交进仓库），Cloudflare 官方文档对「不使用框架预设」的建议是把 **Build command** 填 `exit 0`，**Build output directory** 仍然填 `dist`。

### 4.2 路径 B：直接上传 dist（不接 Git）

先在自己电脑上把站点构建好：

```bash
cd <你的仓库根目录>
npm run build
```

构建完成后，仓库根目录会多出 `dist/` 文件夹，里面是完整站点（含 `index.html`）。

**B1 拖拽上传（推荐给新手）**

1. Cloudflare 控制台 → **Workers & Pages** → **Create application** → **Get started** → **Drag and drop your files**。
2. 在 **Project name** 里填项目名，例如 `ustb-winter-team`。
3. 把 `dist` **文件夹本身**拖进上传框（不要只拖文件夹里的文件，也不要拖成 zip 里的散文件）。
4. 点 **Deploy site**。上传框处理完后点 **Save and Deploy**。
5. **看到什么算成功**：跳到项目页，Deployments 里有一条状态为 Success 的部署，`ustb-winter-team.pages.dev` 能打开。

**B2 用 Wrangler 命令行上传**

前提：电脑上已装 Node.js（本项目构建已经需要它）。

```bash
# 第一次需要登录，会打开浏览器让你授权
npx wrangler login

# 部署 dist 目录；--project-name 换成你的项目名
npx wrangler pages deploy dist --project-name=ustb-winter-team
```

**看到什么算成功**：终端最后一屏打印出一个 `*.pages.dev` 网址，并且提示部署成功。

> 路径 B 每改一次内容都要重新走一遍「构建 + 上传」。日常流程见第九部分。
> 若你的界面里找不到 **Drag and drop your files**，就找含 **Upload** / **Direct Upload** 字样的入口。

## 五、绑定自定义域名（含 DNS 记录表）

这一步有严格的先后顺序，**顺序错了会得到 522 错误**（Cloudflare 官方文档明确警告：先手动加 CNAME 而不在 Pages 里关联域名，域名会解析失败并显示 522）。

### 5.1 第一步（不能跳过）：在 Pages 项目里添加域名

1. 控制台 → **Workers & Pages** → 选中你的 Pages 项目。
2. 点 **Custom domains** 标签。
3. 点 **Set up a domain**。
4. 填你要绑定的域名（先填根域名，例如 `example.com`），点 **Continue**。
5. 按提示继续。此时可能出现两种情况：
   - 你的域名**已经在 Cloudflare**（NS 已指向 Cloudflare，或在 Cloudflare Registrar 购买）：Cloudflare 会**自动**为你创建对应的 DNS 记录，你几乎不用做别的。
   - 你的域名**不在 Cloudflare**：界面会让你去 DNS 服务商添加记录，或者在根域名的情况下先要求你把 nameserver 迁到 Cloudflare。按下面 5.2 / 5.3 做。
6. 然后同样再添加一次 `www.example.com`（作为第二个自定义域名）。这样 www 与裸域都能打开。
7. **看到什么算成功**：Custom domains 列表里出现这两个域名，状态从 Pending 变为 **Active**（说明证书签发完成）。签发通常几分钟，偶尔更久。

### 5.2 做法一：把 nameserver（NS）迁到 Cloudflare（**根域名必须这样做**）

这是官方文档给出的根域名（apex，如 `example.com`）方案：根域名要作为自定义域名使用，这个域名必须是**你这个 Cloudflare 账号下的一个 zone（站点）**，也就是 NS 必须指向 Cloudflare。

1. Cloudflare 控制台 → **Domains** → **Onboard a domain**（旧界面上这个按钮可能叫 **Add a site** / **添加站点**，是同一件事）。
2. 输入你的根域名 `example.com`，选择添加 DNS 记录的方式（可以让它自动扫描，也可以手动填）。
3. 选 **Free** 计划，继续。
4. Cloudflare 会给你**两个专属的 nameserver 地址**，形如：
   - `xxx.ns.cloudflare.com`
   - `yyy.ns.cloudflare.com`

   这两个值每个人都不一样，**以你页面上显示的为准，不要照抄别人的**。
5. 回到买域名的注册商（阿里云 / 腾讯云 / Namecheap 等）的域名管理页面，找到「DNS 服务器 / DNS Servers / nameserver」设置，把原来的两条改成上面 Cloudflare 给的两条，保存。
   - 阿里云：域名控制台 → 你的域名 → **DNS 修改**（把「阿里云DNS」改成「自定义DNS」，填 Cloudflare 的两条）。
   - 腾讯云：域名管理 → 你的域名 → **DNS 服务器** → 自定义。
   - Namecheap：Domain List → 你的域名 → **Manage** → **NAMESERVERS** → 选 **Custom DNS**，填两条。
6. 等生效（通常几分钟到几小时，官方给的最长窗口是 24–48 小时）。Cloudflare 会发邮件告诉你站点已激活。
7. 回到 5.1 再执行一次 **Set up a domain**。这次因为域名已是 Cloudflare 上的 zone，**Cloudflare 会自己创建 CNAME 记录**，你不用手填。

迁移 NS 前务必先做一件事：**在迁走之前，把你原 DNS 上所有还在用的记录看一遍**（例如你用在别处的邮箱域名验证记录、其他子域名）。迁到 Cloudflare 后这些记录要重建，否则会断。

### 5.3 做法二：留在原注册商，只加 CNAME（只适用于子域名 / www）

官方文档给的形态很简单：给子域名加一条 CNAME，指向你的 `*.pages.dev`。

| 类型 | 名称（主机记录） | 目标值（记录值） | 代理状态 | TTL |
| --- | --- | --- | --- | --- |
| `CNAME` | `www`（即 `www.example.com`） | `ustb-winter-team.pages.dev` | 原 DNS 无此开关，留空；若该 DNS 也支持代理则选「仅 DNS」 | 自动 / 600 |

注意三点：

- 目标值**不要**带 `https://`，也不要带结尾的斜杠，就写 `ustb-winter-team.pages.dev`。
- 加完这条记录后，回到 5.1 里把 `www.example.com` 添加为自定义域名，两者**必须都做**。
- **根域名用 CNAME 是不被 DNS 协议允许的**，所以在「不迁 NS」的前提下，裸域 `example.com` 通常接不上 Pages。有些 DNS 服务商提供 `ALIAS` / `ANAME` 这类「根域名 CNAME」记录，可以填：

| 类型 | 名称 | 目标值 | 说明 |
| --- | --- | --- | --- |
| `ALIAS` 或 `ANAME` | `@`（根域名） | `ustb-winter-team.pages.dev` | 只有你的 DNS 服务商支持这种记录类型时才能用；多数国内 DNS 在根域名上只给 A 记录，此时请改用 5.2 迁 NS |

**若你的界面与上文不同**：在 DNS 记录页面里找含 **CNAME** 字样的记录类型下拉框；「代理状态」这一栏在你把域名托管到 Cloudflare 时表现为一个**橙色云朵开关**（橙色=经 Cloudflare 代理，灰色=仅 DNS，即「DNS only」）。在没有代理概念的原注册商 DNS 上，这一栏不存在，留空即可。

### 5.4 域名已在 Cloudflare 托管时的完整记录表（可直接照抄结构）

在 **DNS → Records** 页面里，正常情况下你会看到（或需要补上）这样两条：

| 类型 | 名称 | 内容 | 代理状态 | TTL |
| --- | --- | --- | --- | --- |
| `CNAME` | `@`（即 `example.com`） | `ustb-winter-team.pages.dev` | 已代理（橙色云） | 自动 |
| `CNAME` | `www` | `ustb-winter-team.pages.dev` | 已代理（橙色云） | 自动 |

说明：

- 根域名位置上的 CNAME 由 Cloudflare 内部做「CNAME 拉平」，所以你在根域名写 CNAME 是合法的，浏览器最终拿到的是 A 记录。
- 如果你的页面里出现的是 `AAAA` 记录或指向怪 IP 的记录，别手动改，先看 5.1 是否已成功添加自定义域名——Cloudflare 自动生成的记录不要动。
- 只想让站点通过 Cloudflare 走（要开 HTTPS 强制跳转、要清缓存）就必须是**橙色云**；改成灰色云会绕过 Cloudflare 的证书与规则功能。

### 5.5 怎么确认解析真的对了

在电脑上开一个终端（Windows 用 PowerShell 或 CMD 都可以）：

```bash
nslookup www.example.com 1.1.1.1
nslookup example.com 1.1.1.1
```

**看到什么算成功**：两条命令都能返回结果，且 `www` 那条输出的 `Canonical name` 里出现 `ustb-winter-team.pages.dev`。如果返回「找不到」，说明记录还没生效或写错了，等 10 分钟再试。

### 5.6 日后在同一域名下加页面 / 换内容，会影响已绑定的域名吗？

**不会。** 域名绑定是**项目级**的，不是页面级的。

- 你在 Pages 里绑定的是「`example.com` 这个域名 → `ustb-winter-team` 这个项目」，而不是某个具体页面。
- 因此：新增页面（比如再做一个「常见问题」页）、删除页面、大改「小队介绍」的文案、换配色、换图片，**都不需要重新配置域名**，DNS 记录和 Custom domains 里的两条记录保持原样不动。
- 你需要做的只有一件事：**重新构建并部署**（路径 A 是 push 代码，路径 B 是重新上传 `dist`）。部署完成后新页面立即可访问，网址规则照旧。
- 唯一需要注意的：**不要改 Pages 的项目名**，也不要动 Custom domains 里的域名，这两样才是和域名绑在一起的。改页面文件本身完全安全。
- 如果新页面的网址是 `example.com/qa/` 这种，能不能打开只取决于构建产物里有没有对应文件（例如 `dist/qa/index.html`），和域名无关。

一句话记法：**域名绑的是项目，内容改的是文件；改文件不用碰域名。**

## 六、HTTPS / 证书 / 强制 https 跳转

### 6.1 证书是自动的

绑定好自定义域名后，Cloudflare 会为它自动签发并续期 TLS 证书，你不需要上传任何证书文件。判断方法：**Custom domains** 页面里域名旁边的状态变成 **Active**，同时浏览器访问 `https://example.com` 显示小锁。

证书签发被卡住最常见的原因是 **CAA 记录**。如果你的域名上有 CAA 记录，且不允许 Cloudflare 使用的 CA 签发，证书就会一直不生效。官方文档给出的放行写法（在 DNS 里加这几条即可，值照抄）：

```text
example.com.  300  IN  CAA  0 issue     "letsencrypt.org"
example.com.  300  IN  CAA  0 issue     "pki.goog; cansignhttpexchanges=yes"
example.com.  300  IN  CAA  0 issue     "ssl.com"
example.com.  300  IN  CAA  0 issuewild  "letsencrypt.org"
example.com.  300  IN  CAA  0 issuewild  "pki.goog; cansignhttpexchanges=yes"
example.com.  300  IN  CAA  0 issuewild  "ssl.com"
```

如果你从来没加过 CAA 记录，那就不用管这一节。

### 6.2 强制 http → https 跳转

官方步骤：

1. 控制台进入域名（zone），点 **SSL/TLS** → **Overview**。
2. 确认加密模式不是 **Off**（Off 状态下下面那个开关根本不会显示）。
3. 切到 **Edge Certificates** 页面。
4. 打开 **Always Use HTTPS**。

**看到什么算成功**：在浏览器地址栏输入 `http://example.com`（注意是 http），回车后地址栏自动变成 `https://example.com/`。

**若你的界面与上文不同**：在域名设置里找含 **Always Use HTTPS** 字样的开关；或者找 **SSL/TLS → Edge Certificates** 这个组合。

### 6.3 一个可选项（不懂就别开）

**HSTS**（在同一个 Edge Certificates 页面）会让浏览器在很长时间内强制只用 https 访问你的域名，配错后很难回退。小队站不需要它，**保持关闭**。

## 八、常见故障排查表

| 现象 | 最可能的原因 | 怎么确认 | 怎么修 |
| --- | --- | --- | --- |
| 打开域名是 404 页面 | 构建产物的**输出目录填错**（例如填了 `public` 或留空，而实际产物在 `dist`）；或 `index.html` 不在产物根目录 | 项目 → **Deployments** → 打开最新一次部署的详情，看输出文件列表里有没有 `index.html` | Settings 里把 **Build output directory** 改为 `dist`，重新部署 |
| 三个页面里某一个 404 | 那次构建的产物里没有对应文件（页面文件命名/目录不对，或 `build.mjs` 没把它输出） | 本地 `npm run build` 后看 `dist/` 里有没有该页面的 `index.html` | 修正页面文件位置后重新构建部署；一次性排查可本地打开 `dist/index.html` 点一遍 |
| 打开域名是 522 错误 | 手动加了 CNAME 但**没有**先在 Pages 里添加自定义域名 | **Custom domains** 里没有这个域名 | 先做 5.1，再等状态变 Active |
| 打开域名是 522，且自定义域名已添加 | 根域名不是当前账号下的 Cloudflare zone（NS 没迁过来） | NS 是否已指向 Cloudflare 给的两条 | 按 5.2 迁 NS |
| 证书一直 pending / 状态迟迟不变 Active | 有 CAA 记录挡了签发；或 NS / CNAME 还没生效；或域名刚改过解析 | 用 5.5 的命令确认解析；看 DNS 里有没有 `CAA` 记录 | 加 6.1 的 CAA 放行记录；等解析生效；必要时移除该自定义域名后重新添加 |
| DNS 未生效 | TTL 未过；本地或运营商的 DNS 缓存；NS 刚改（最长 24–48 小时） | `nslookup www.example.com 1.1.1.1` 与 `nslookup www.example.com` 对比；用手机流量再试 | 换 1.1.1.1 或 8.8.8.8 验证；等待；确认主机记录与值没有多余空格 |
| 改了内容，线上还是旧版 | ① 构建根本没触发（改了别的分支 / 自动部署被关 / 提交没推送成功）② Cloudflare 缓存 ③ 浏览器缓存 | 看 **Deployments** 里最新一条的时间戳是不是你刚才那次；在无痕窗口打开 | 确认 commit 已推送到 production 分支；在域名下清缓存（找含 **Purge** 字样的入口，通常是 **Caching** → **Purge Everything**）；Ctrl+F5 / 无痕窗口 |
| 域名解析被污染（部分网络打不开，或打开是别的页面） | 本地 DNS 被劫持或该运营商线路异常；也可能只是你的网络问题 | 用 1.1.1.1 与本地默认 DNS 各查一次，看返回 IP 是否一致；换手机流量对比；用第三方多地解析检测工具看各地结果 | 先排除本地 DNS：把电脑 DNS 改成 `1.1.1.1` 再试；若确认是多地解析异常，这属于线路层面的问题，长期方案涉及域名与线路选择，**超出本文范围，需单独评估**（且注意：改用境内 CDN 会触发第三部分的备案要求） |
| `www` 与裸域内容不一致 / 其中一个打不开 | 只添加了其中一个自定义域名；或另一个还停在旧的 A 记录 | **Custom domains** 里只有一条 | 两个域名都添加为自定义域名；再在 **Rules → Redirect Rules**（单条跳转）里做一条 301，把 `www` 统一跳到裸域（或反过来），避免两套地址各算一份流量 |
| 页面文件名用中文，链接打不开 | 文件名/链接里的中文被转义后不一致，或大小写不一致 | 对照 `dist` 里的实际文件名 | 页面文件名用英文或拼音（例如 `qa/index.html`），重新构建部署 |
| 部署成功但样式全丢 | 资源用了站点根绝对路径，但站点被部署在子路径下；或 `public/` 里的静态资源没被复制进 `dist/` | 按 F12 看 Console 与 Network 里 404 的资源 | 修正构建输出或资源路径后重新部署 |

## 九、日常发布流程

改内容之后的固定动作，照做即可，不用重新理解。

### 9.1 走路径 A（Git 自动部署）时

1. 修改站点里的页面文件（例如「小队介绍」的文案、加一份新的资料链接）。**不需要动域名配置**（见 5.6）。
2. 本地构建一次，先自己看一眼（可选但推荐）：
   ```bash
   npm run build
   ```
   然后直接打开 `dist/index.html` 逐个页面点一遍。
3. 提交并推送：
   ```bash
   git add .
   git commit -m "update: 小队介绍补入寒招行程"
   git push
   ```
4. 回到 Cloudflare → 你的项目 → **Deployments**，会看到一条新部署自己开始跑。
5. **看到什么算成功**：这条部署状态变 **Success**，点开它的预览地址能看到新内容。
6. 打开你的域名，看不到新内容时按 Ctrl+F5（或开无痕窗口）再确认；仍然不对就看第八部分「改了内容，线上还是旧版」。

### 9.2 走路径 B（直接上传）时

1. 改页面文件。
2. `npm run build`。
3. 打开 Cloudflare 项目页 → **Create a new deployment** → 把新的 `dist` 拖进去 → 部署；或者命令行 `npx wrangler pages deploy dist --project-name=ustb-winter-team`。
4. 确认 Deployments 最新一条是你刚上传的，状态 Success。

### 9.3 发布出问题时的一键回退

1. 项目 → **Deployments** → 在 **All deployments** 列表里找到上一个正常的部署。
2. 点它右侧的 **三个点** 菜单 → **Rollback to this deployment** → 确认。
3. **看到什么算成功**：Production 立刻变回那个版本，刷新域名就是旧版内容。注意预览部署（Preview）不能作为回退目标。

### 9.4 交接与长期维护（小队站特别重要）

- 域名开启自动续费，并在日历里记下到期日前 2 周的提醒——域名过期被释放是最贵的一类事故。
- 把 Cloudflare 账号、注册商账号、域名、项目名写成一张交接清单，交给下一届负责人；寒招小队每年换届，这一步比技术细节更关键。
- `dist/` 是构建产物，建议不要提交进 Git 仓库（用 `.gitignore` 忽略它）。这样仓库里只有页面源码，历史清爽。**这条建议涉及改 `.gitignore`，本指南不替你改，你确认后自行决定。**
